# AGENTS.md — axum-live-view

## Project Overview

**axum-live-view** is a Rust workspace implementing a **Phoenix LiveView**-style framework for the [axum](https://github.com/tokio-rs/axum) web framework. It allows building real-time, server-rendered HTML applications entirely in Rust — no JavaScript or WASM required.

- **Repository:** https://github.com/davidpdrsn/axum-live-view
- **Status:** Early-stage / work-in-progress
- **Rust edition:** 2024

## Key Concepts

### 1. The `LiveView` Trait (`live_view/mod.rs`)

The central contract. Users implement this for their state struct:

```rust
pub trait LiveView: Sized + Send + Sync + 'static {
    type Message: Serialize + DeserializeOwned + PartialEq + Send + Sync + 'static;
    fn mount(&mut self, uri: Uri, request_headers: &HeaderMap, handle: ViewHandle<Self::Message>) {}
    fn update(self, msg: Self::Message, data: Option<EventData>) -> Updated<Self>;
    fn render(&self) -> Html<Self::Message>;
}
```

- `mount()` is called once when the WebSocket connects; receives a `ViewHandle` for async message injection
- `update()` is synchronous; called for every client event
- `render()` is called after every `update()` and the initial render

### 2. `Updated<T>` Return Type

Returned from `update()`:
- `Updated::new(view)` — no side effects
- `.with(js_command)` — add a JsCommand
- `.with_all(iter)` — add multiple JsCommands
- `.spawn(future)` — spawn an async future that eventually yields a Message (ignored in tests)

### 3. HTML Representation

`Html<T>` is essentially a **static/dynamic interleaved tree**:
- `fixed: &'static [&'static str]` — array of static HTML string slices
- `dynamic: BTreeMap<usize, DynamicFragment<T>>` — map of index → dynamic content

`DynamicFragment<T>` variants:
- `String(String)` — a dynamic string (from `{ expr }` blocks that impl Display)
- `Message(T)` — a serialized message (from `axm-*` attributes)
- `Html(Html<T>)` — nested `Html` (from nested `html!` calls)
- `Loop { fixed, dynamic }` — a `for` loop with body templates

### 4. The `html!` Macro (`axum-live-view-macros/src/lib.rs`)

A proc-macro that parses HTML-like syntax inside Rust code. Key implementation details:

**Parsing architecture:**
- `Tree` → `Vec<HtmlNode>` (root nodes)
- `HtmlNode` enum: `Doctype`, `TagNode`, `LitStr`, `Block`, `If`, `For`, `Match`
- `TagNode` has `open: Ident`, `attrs: Vec<Attr>`, `close: Option<TagClose>`
- `Attr` is either `Normal { ident, value }` or `Axm { ident, value }`

**Attribute parsing:**
- `AttrIdent` distinguishes `Axm(String)` (prefixed with `axm-`) from `Lit(String)` (all others)
- Known `axm-*` bindings: `click`, `input`, `change`, `submit`, `focus`, `blur`, `keydown`, `keyup`, `window-keydown`, `window-keyup`, `window-focus`, `window-blur`, `mouseenter`, `mouseover`, `mouseleave`, `mouseout`, `mousemove`, `scroll`
- `throttle`, `debounce`, `key` are recognized as `Lit` (non-axm)
- Unrecognized `axm-*` attributes produce a compile error

**Keyword handling:**
- `type` and `for` are special-cased in `AttrIdent::parse` to be treated as literal attribute names despite being Rust keywords

**Optional attributes:**
- `Some(expr)` / `None` syntax on `NormalAttrValue`: `Some("value")` includes the attr, `None` omits it, `Some(())` includes as boolean attr, `Some(Option::None)` omits

**`if` in attributes:**
- `axm-click=if cond { Msg::A } else { Msg::B }` is supported
- Normal attrs support `if cond { "a" } else { () }`

**Output generation (`NodeToTokens` trait):**
- Each node type implements `node_to_tokens(&self, fixed: &mut FixedParts, out: &mut TokenStream)`
- `FixedParts` accumulates static HTML strings; when a dynamic part is encountered, `start_new_part()` starts a new static string
- Final output: `HtmlBuilder { dynamic: __dynamic, fixed: &[#parts...] }.into_html()`
- Dynamic fragments are pushed via `DynamicFragmentVecExt` methods: `push_fragment`, `push_message`, `push_fragments`

**`for` loops:**
- Generate a `for pat in expr { ... }` that collects `Vec<Vec<DynamicFragment>>` (one inner Vec per iteration)
- The inner Vec is created by running the template body's `node_to_tokens` in a fresh scope
- Result is passed to `push_fragments(fixed_parts, dynamic_loop_parts)`

**`match`:**
- Arms push via `__dynamic.push_fragment(#tree)`

### 5. Client-Server Protocol (`life_cycle.rs`)

Communication happens over WebSocket using JSON messages with compact single-letter field names:

**Server → Client (`MessageToSocket`):**
```json
{"t": "i", "d": <Html>}     // InitialRender
{"t": "r", "d": <Diff>}     // Render (diff)
{"t": "j", "d": [<JsCmd>]}  // JsCommands
{"t": "h"}                   // Health (heartbeat)
```

**Client → Server (`MessageFromSocket`):**
```json
{"m": "%22Incr%22", "t": "click"}                              // Event with click
{"m": "%22Incr%22", "t": "form", "d": {"q": "name=bob&age=20"}} // Event with form data
{"t": "h"}                                                       // Health (heartbeat)
```

- Messages (`m` field) are **percent-encoded JSON** strings deserialized with a custom `deserialize_msg` visitor
- Event data is tagged by `t` with optional `d` payload

### 6. HTML Diffing (`html/diff.rs`)

`Html::diff(&self, other) -> Option<HtmlDiff>` performs a structural diff:

- `HtmlDiff` mirrors the `Html` structure but with `Option` for removals
- Comparisons: strings by equality, messages by `PartialEq`, nested HTML recursively, loops by comparing each iteration
- The `zip` function uses `map_while` with `repeat(None)` to handle iterators of different lengths (Left = removed, Right = added, Both = compared)
- **Important:** `Loop` diff format uses `"f"` for fixed part changes and `"b"` for per-iteration body diffs (indexed by iteration index)
- Diff structure is serialized directly to JSON for minimal wire format
- `diff_fixed` returns `&[]` if arrays are equal, or the new array if different

### 7. Life Cycle Runtime (`life_cycle.rs`)

**`spawn_view(view, view_handle) -> ViewTaskHandle`:**
- Spawns a `tokio::spawn` task that owns the view
- Receives `ViewRequest` messages via `mpsc::channel(1024)`
- Handles: `Mount`, `Render`, `RenderToString`, `Update`
- On `Update`: calls `view.update()`, diffs old vs new markup, returns `UpdateResponse`
- Wraps all markup in `<div id="live-view-container">...</div>`

**`run_view(write, read, view, uri, headers)`:**
- The main event loop running per-WebSocket-connection
- Merges two streams: WebSocket events and `ViewHandle` messages (via `ReceiverStream`)
- On event: calls `view.update()`, produces diff/JsCommands, writes to socket
- On internal health: responds with health message (heartbeat)

**`UpdateResponse` enum:**
- `Diff(Value)` — only a diff
- `JsCommands(Vec<JsCommand>)` — only commands
- `DiffAndJsCommands(Value, Vec<JsCommand>)` — both
- `Empty` — no changes, nothing sent

### 8. ViewHandle (Async Message Injection)

`ViewHandle<M>` wraps an `mpsc::Sender<M>`. Key methods:
- `send(msg)` — sends a message to `update()`
- `forward(stream)` — forwards all items from a stream
- `with(f, mapper)` — creates a new `ViewHandle<M2>` that maps messages via `f: Fn(M2) -> M` (spawns a cheap forwarding task)

### 9. Combine (`live_view/combine.rs`)

`combine::Combine<V, F>` allows combining up to 8 views into one. **This file is auto-generated** by `cargo xtask codegen` (see `xtask/src/main.rs`).

- `Either1`–`Either8` enums wrap individual message types
- Each implementation pattern: delegate `mount`/`update`/`render` to the appropriate sub-view, mapping messages through the `Either` variant
- The `render` closure receives each sub-view's HTML already mapped to the combined message type
- Note: the `spawn` futures in `update` also need message-remapping via `Box::pin`

## Extractor Flow (`extract.rs`)

`LiveViewUpgrade` implements `FromRequestParts`:
- Checks if the request is a WebSocket upgrade (`WebSocketUpgrade::from_request_parts`)
- If yes → stores `WebSocketUpgrade`, `Uri`, `HeaderMap`
- If no → stores nothing (`Http` variant)

`LiveViewUpgrade::response(gather_view)`:
- On HTTP: calls `gather_view(EmbedLiveView::noop())` and returns rendered HTML as `Response`
- On WebSocket: calls `gather_view(EmbedLiveView::new(&mut view))`, then upgrades via `ws.on_upgrade(move |socket| run_view_on_socket(socket, view, uri, headers))`

`EmbedLiveView`:
- `embed(view)` — renders the view, wraps in container div, stores view in `Option<L>` for later use
- `connected()` — returns whether this is a WebSocket connection (view was stored)

## Event Data (`event_data.rs`)

Events from the client deserialize into `EventData`:
- `Form { query }` — URL-encoded query string, deserializable via `Form::deserialize::<T>()`
- `Input { .. }` — `Bool(bool)`, `String(String)`, `Strings(Vec<String>)`
- `Key { key, code, alt, ctrl, shift, meta }`
- `Mouse { client_x, client_y, page_x, page_y, offset_x, offset_y, movement_x, movement_y, screen_x, screen_y }`
- `Scroll { scroll_x, scroll_y }`

Each has a builder type (e.g., `KeyBuilder`, `MouseBuilder`) and `builder()` constructor.

`EventMessageFromSocketData` maps to `Option<EventData>` — `Click`, `WindowFocus`, `WindowBlur`, and `None` produce `None`.

## JavaScript Commands (`js_command.rs`)

`JsCommand { kind, delay_ms }`:
- `navigate_to(uri)` → `window.location`
- `add_class(selector, class)` / `remove_class` / `toggle_class`
- `clear_value(selector)` — clear input fields
- `set_title(title)` — change `<title>`
- `history_push_state(uri)` → `History.pushState`
- `.delay(Duration)` chains optional delay via `setTimeout`

## Testing (`test.rs`)

```rust
let handle = run_live_view(MyView::default())
    .mount_uri("/custom".parse().unwrap())
    .mount_headers(headers)
    .mount()
    .await;

let html = handle.render().await;               // current HTML
let (html, js_commands) = handle.send(msg, data).await;  // send message, get updated HTML
```

- `spawn_view` creates the background task with `view_handle = None` — so `Updated::spawn` futures are silently dropped; use `ViewHandle::send` from tests instead
- Note: the `ViewHandle` passed to `mount` in tests is a fake (its rx is immediately dropped), so `ViewHandle::send` from within `mount` will always fail

## Code Generation Details

The `combine.rs` file is entirely generated by `cargo xtask codegen`. If you need to modify the combine logic:
1. Edit `xtask/src/main.rs` → `codegen()` function
2. Run `cargo xtask codegen`
3. The output is written to `axum-live-view/src/live_view/combine.rs` and auto-formatted

The generated code follows a mechanical pattern: for each arity 1–8, generate an `EitherN` enum and a `LiveView` impl for `Combine<(T1..TN), F>`.

## Vendored Code

Two files are vendored from `tokio-stream` to avoid version conflicts:
- `util/receiver_stream.rs` — `ReceiverStream<T>` wrapping `tokio::sync::mpsc::Receiver`
- `util/stream_ext.rs` — `StreamExt::merge()` with `Merge` and `Fuse` implementations

## Important Notes for Contributors

1. **Rust edition 2024** — requires nightly or very recent stable Rust
2. **`tokio_unstable`** cfg is used; `Receiver::poll_recv` is used directly
3. The `html!` macro does NOT use a real HTML parser — it's a custom parser that handles a subset of HTML-like syntax interleaved with Rust control flow
4. All messages are percent-encoded JSON strings over the wire
5. The HTML diff format is an internal protocol; the JavaScript client consumes it directly
6. The `__private` module (`html/private.rs`) is the boundary between the proc-macro and runtime — the macro generates code that uses `HtmlBuilder`, `DynamicFragmentVecExt`, and `DynamicFragment`
7. When adding new `axm-*` bindings, update the list in `AttrIdent::parse` in `axum-live-view-macros/src/lib.rs`
8. The `spawn` futures in `Updated` are silently dropped in test mode (and also in the `ViewHandle::with` forwarding task) — this is by design
